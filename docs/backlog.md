## B. 機能の候補

| 優先度(提案) | 機能 | 内容・メモ |
| --- | --- | --- |
| 高 | ノード単位の start / stop / wipe のUI | APIは実装済み。`wipeNode()` は既存ラボのトポロジ取得（`topology/yaml`）が必要で未着手 |
| 高 | キャプチャ残留コンテナの確実な掃除 | 現状はブラウザ側のポーリング頼み。サーバー側で「一定時間無通信なら削除」するのが確実（capture-proxyでWS切断を検知して遅延削除、またはcronで古い `clab_ws_vnc_*` を回収） |
| 中 | 自動保存（CML風） | 現在は Deploy ボタン起点。継続的な保存の価値は高いが、実装コストが大きく優先度低と判断済み |
| 中 | BGPの `ebgp-requires-policy` 対策 | 学生が必ずハマる点。READMEで周知 / UIにヒント表示 / FRRのデフォルト設定を変える、のどれにするか未決 |
| 中 | ラボの自動停止（アイドル） | 共有サーバー（RAM 12GB）なので、放置ラボがリソースを食う問題への備え |
| 中 | キャプチャのフィルタ指定 | 開始時に表示フィルタ/キャプチャフィルタを渡せると使いやすい（pcap保存は対象外と判断） |
| 低 | L3スイッチ | FRR＋VLAN対応ブリッジで実現可能だが実装コスト大。将来拡張 |
| 低 | ノードのイメージ選択 | 現在は固定（FRR / OVS / Alpine）。他のコンテナを選べるか |
| 低 | 外部ネットワーク接続 | **スコープ外と決定済み**（実装しない） |

## C. 運用・基盤（卒業制作として押さえたい）

| 項目 | 検討内容 |
| --- | --- |
| 本番形態 | 現在は `vite dev` を手動起動。`vite build` ＋ 静的配信（nginx等）＋ systemd 常駐にするか |
| サービスの常駐 | capture-proxy は systemd (user) 化済み。console-proxy / ovs-helper / vite の扱いを揃える |
| TLS | clab-api-server・capture-proxy は自己署名。console-proxy(ws://) / ovs-helper(http://) は平文。混在コンテンツ（フロントをHTTPS化した場合）の問題に注意 |
| 証明書の警告 | 利用者全員が初回に警告を許可する必要あり。社内CA or Let's Encrypt（ドメイン次第）を検討 |
| ovs-helper の認可 | ユーザーごとの権限確認がどうなっているか再点検（他人のOVSブリッジを触れないか） |
| リソース制限 | ノード数上限は設けない方針だが、メモリ枯渇時の挙動（OOM）と警告の出し方は未検討 |
| 障害時の復旧 | サーバー再起動後にラボ・OVS設定・プロキシが戻るか |
| バックアップ | ラボ定義は `/var/lib/containerlab/labs/<user>/` に保存される。バックアップ方針なし |
| JWT有効期限 | 切れたら再ログイン。UI側の扱い（作業中の編集内容が消えないか）を確認 |
| 自動テスト | 現状は実機での手動確認が中心。最低限、座標/YAML変換などの純粋関数にユニットテストを |

## D. ドキュメント・公開

| 項目 | 内容 |
| --- | --- |
| 利用者向けマニュアル | `test-manual.md` を整えて利用者向けに発展させる |
| セットアップ手順 | 新しいサーバーに入れる手順（Docker / Containerlab / clab-api-server / 各プロキシ / OVS設定）を1本にまとめる。インストールスクリプト化も候補 |
| 公開・配布方針 | OSSとしてどう公開するか（ライセンス、README、デモ動画）。「空き時間に検討」と合意済み、優先度は機能より下 |
| 卒論の整理 | 差別化点（CML相当の操作感＋マルチユーザー＋ノード数無制限）を示す比較・実測データ（起動ノード数とメモリ等）をまとめる |
| 企画・設計書 | チーム情報（サイクル/チーム名/メンバー欄）の記入（コード外タスク） |
